## 2. Preparare il computer (una volta)

```bash
cd <cartella del clone di palestra>      # oppure git clone dell'indirizzo del repository
git config core.hooksPath .githooks      # hook pre-push: blocca i dati personali
test -f ~/.config/palestra/identificativi.txt && echo "pattern personali presenti"
git fetch origin --prune
git switch main && git pull --ff-only
npm ci                                   # Node 22; npm 10 basta per npm ci
npm test && npm run lint && npm run typecheck
```

- **Dipendenze.** Per `npm ci` basta l'npm di Node 22. Per installarne una nuova, solo con il permesso dell'utente, si usa `npx -y npm@11 install …` e poi si verifica con `rm -rf node_modules && npm ci`, perché npm 10.9 si blocca sui peer di vite e vitest. Le motivazioni sono in [`kb/decisioni/2026-10-31-vitest-plugin-al-posto-di-pool-workers.md`](../kb/decisioni/2026-10-31-vitest-plugin-al-posto-di-pool-workers.md).
- **Hook pre-push.** In locale legge `~/.config/palestra/identificativi.txt`, che sta fuori dal repository ([`docs/migrazione.md`](migrazione.md)). Senza quel file controlla solo i percorsi. Se `gitleaks` è installato, cerca anche i segreti.
- **Permessi di Claude Code.** [`.claude/settings.json`](../.claude/settings.json) vale anche in locale: Claude chiede prima di `git push`, `git merge`, `gh pr create`, `npm install`, `wrangler d1 execute` e prima di modificare `.github/workflows/`. Il revisore indipendente è [`.claude/agents/reviewer.md`](../.claude/agents/reviewer.md).
- **Cosa non c'è in locale.** La memoria del Progetto Claude e il connettore Cloudflare non arrivano in VS Code. Contano questo documento, le descrizioni delle PR e `kb/`. Per leggere D1 dal terminale: `npx wrangler login`, poi `wrangler.toml` con `node scripts/render-wrangler.mjs` (legge `D1_DATABASE_ID` dall'ambiente), poi `npx wrangler d1 execute palestra --remote --command "SELECT …"`, solo in lettura.

## 3. Riprendere una corsia

Ogni corsia ha un proprio worktree, così due branch non si pestano i piedi. `git worktree add` crea il branch locale che segue quello remoto:

```bash
git fetch origin
git worktree add ../palestra-task-0 feat/task-0-forma   # stesso schema per le altre corsie
cd ../palestra-task-0 && npm ci && npm test
code .                                              # apre il worktree in VS Code
```

In VS Code si apre il pannello di Claude Code, oppure si lancia `claude` nel terminale integrato, e si incolla il prompt della corsia. Ogni prompt fa leggere a Claude `CLAUDE.md`, questa sezione e l'ultima PR, come chiede la regola 11 di `CLAUDE.md`. Prima di lavorare su un branch in locale conviene fermare il thread cloud che lo usa: le due copie non si sincronizzano (§ 5).

## 5. Portare in locale una sessione cloud (facoltativo)

La via principale è quella del § 3: branch, PR e questo documento. Claude Code permette anche di portare una sessione cloud nel terminale ([documentazione](https://code.claude.com/docs/en/claude-code-on-the-web)):

- `claude --teleport` apre l'elenco delle sessioni cloud; `claude --teleport <id della sessione>` ne riprende una. Dentro una sessione aperta si usa `/teleport`. Il comando controlla repository e account, scarica il branch della sessione e ne fa il checkout, poi carica la conversazione.
- **Requisiti.** Stesso repository, working tree pulito (altrimenti propone lo stash), branch già pubblicato, stesso account claude.ai: non funziona con una chiave API.
- **In VS Code.** L'estensione mostra le sessioni cloud nella cronologia, scheda Web, ma ne scarica solo la conversazione, senza checkout del branch. Per il checkout serve `claude --teleport` nel terminale integrato, con la CLI installata a parte ([VS Code](https://code.claude.com/docs/en/vs-code)).
- **Limiti.**
  - Dopo il teleport le copie sono due e non si sincronizzano: il lavoro locale non compare nella sessione cloud.
  - I thread di un Progetto Claude non sono disponibili nella CLI né in VS Code, e il loro teleport non è documentato.
  - Per i thread di questo progetto la via sicura resta quella del § 3. Prima conviene fermare il thread cloud e fargli pubblicare il branch.

## 6. Regole da tenere presenti

- **Branch e merge.** Mai lavorare su `main`. Una PR per task, in bozza, assegnata all'utente; il merge con squash lo fa l'utente, salvo una sua indicazione diversa. Dopo ogni merge, riallineare gli altri branch a `main` con un merge, senza force push.
- **Proprietà dei file.**
  - `src/store/planning.ts` e `src/domain/metrics.ts` nascono dal Task 6.
  - `src/mywellness/client.ts`, i suoi test MSW e `docs/mywellness-api.md` appartengono alla corsia della #52.
  - Chi ha bisogno di una funzione di un'altra corsia non la scrive: la segnala nella propria PR.
- **Dati personali.** Nei testi si scrive «l'utente» e `<DASHBOARD_HOSTNAME>`. I log pubblici di Actions contengono solo conteggi, durate ed exit code. Non si scrive mai a mano su `sessions` e `timeseries`, e un `DELETE` su D1 richiede la conferma esplicita dell'utente.
- **Evidenza.** Prima di dire «fatto» si incolla l'output di `npm test`, `npm run lint` e `npm run typecheck` con l'exit code. La revisione indipendente la fa `.claude/agents/reviewer.md`, che riceve solo gli SHA, la spec, il task e `CLAUDE.md`.
