## 2. Preparare il computer (una volta)

Servono Node 22, git, VS Code con l'estensione Claude Code e la CLI `claude` installata a parte: l'estensione non la mette nel `PATH`, e la CLI serve per il terminale e per il § 5. Su macOS il comando `code` si installa da VS Code (Command Palette → «Shell Command: Install 'code' command in PATH»).

```bash
cd <cartella del clone di palestra>      # oppure git clone dell'indirizzo del repository
git config core.hooksPath .githooks      # hook pre-push: blocca i dati personali
test -f ~/.config/palestra/identificativi.txt && echo "pattern personali presenti" \
  || echo "MANCA ~/.config/palestra/identificativi.txt: crearlo prima del primo push"
git fetch origin --prune
git switch main && git pull --ff-only
npm ci                                   # Node 22; npm 10 basta per npm ci
npm test && npm run lint && npm run typecheck
```

- **Hook pre-push.** Legge `~/.config/palestra/identificativi.txt`, che sta fuori dal repository: una regex per riga, con nome, cognome, e-mail, telefono, dominio e data di nascita ([`docs/migrazione.md`](migrazione.md)). Senza quel file, e senza la variabile `PII_PATTERNS`, lo script di controllo esce con 78 e l'hook blocca ogni push. Il file va creato prima del primo push. L'hook non si aggira mai, né con `--no-verify` né con un `PII_PATTERNS` che non trova nulla. Se `gitleaks` è installato, l'hook cerca anche i segreti.
- **Dipendenze.** Per `npm ci` basta l'npm di Node 22, lo stesso della CI. Una dipendenza nuova si installa solo con il via esplicito dell'utente. Si usa `npx -y npm@11 install …`, perché npm 10.9 va in errore (`edgesOut`) sulle dipendenze di vite ([nota KB](../kb/decisioni/2026-10-31-vitest-plugin-al-posto-di-pool-workers.md)), e poi si verifica con `npm ci`, che ricrea `node_modules` da solo. La regola ask di `.claude/settings.json` copre `npm install`, non `npx -y npm@11 install`.
- **Permessi di Claude Code.** [`.claude/settings.json`](../.claude/settings.json) vale anche in locale. Claude chiede prima di `git push`, `git merge`, `gh pr create`, `npm install`, `wrangler d1 execute` e prima di modificare `.github/workflows/`. Il revisore indipendente è [`.claude/agents/reviewer.md`](../.claude/agents/reviewer.md).
- **Cosa non c'è in locale.** La memoria del Progetto Claude e il connettore Cloudflare non arrivano in VS Code. Contano questo documento, le descrizioni delle PR e `kb/`. Per leggere D1 dal terminale bastano `npx --no -- wrangler login` e poi `npx --no -- wrangler d1 execute palestra --remote --command "SELECT …"`, dalla radice e solo in lettura: wrangler trova il database per nome.

## 3. Riprendere una corsia

Ogni corsia ha un proprio worktree, così due branch non si pestano i piedi. Questo documento è su `main` dopo il merge della sua PR (#61). Nei worktree di un branch più vecchio arriva con il riallineamento a `main`, che serve comunque prima di ogni merge:

```bash
git fetch origin
git worktree add ../palestra-task-0 feat/task-0-forma   # branch esistente: lo segue da origin
cd ../palestra-task-0 && git merge origin/main          # riallineamento, senza force push
npm ci && npm test && code .                            # code . apre il worktree in VS Code
# corsia nuova, per esempio la #52 con il canale A:
git worktree add -b feat/issue-52-api ../palestra-issue-52 origin/main
```

In VS Code si apre il pannello di Claude Code, oppure si lancia `claude` nel terminale integrato, e si incolla il prompt della corsia. Come chiede la regola 11 di `CLAUDE.md`, ogni prompt fa leggere `CLAUDE.md`, il piano e la PR della corsia, con la sua descrizione e l'ultimo commento.

Prima di lavorare in locale su un branch si chiede al thread cloud che lo usa di pubblicare l'ultimo commit e di smettere di osservare la PR, oppure si archivia il thread; poi `git pull` nel worktree. Un thread fermo che osserva la PR si risveglia a ogni evento di CI o di revisione e potrebbe pubblicare sullo stesso branch.

## 5. Portare in locale una sessione cloud (facoltativo)

La via principale è quella del § 3: branch, PR e questo documento. Claude Code permette anche di portare una sessione cloud nel terminale ([documentazione](https://code.claude.com/docs/en/claude-code-on-the-web)):

- `claude --teleport` apre l'elenco delle sessioni cloud; `claude --teleport <id della sessione>` ne riprende una. Dentro una sessione aperta si usa `/teleport`. Il comando controlla repository e account, scarica il branch della sessione e ne fa il checkout, poi carica la conversazione.
- **Requisiti.** Stesso repository, working tree pulito (altrimenti propone lo stash), branch già pubblicato, stesso account claude.ai: non funziona con una chiave API.
- **In VS Code.** L'estensione mostra le sessioni cloud nella cronologia, scheda Web, ma ne scarica solo la conversazione, senza checkout del branch. Per il checkout serve `claude --teleport` nel terminale integrato ([VS Code](https://code.claude.com/docs/en/vs-code)).
- **Limiti.**
  - Dopo il teleport le copie sono due e non si sincronizzano: il lavoro locale non compare nella sessione cloud.
  - I thread di un Progetto Claude non sono disponibili nella CLI né in VS Code, e il loro teleport non è documentato. Per questi thread la via sicura resta quella del § 3.
  - In alternativa il Progetto può far lavorare un suo thread sul computer dell'utente con Remote Control, dopo l'approvazione dall'app: il thread resta nel Progetto, ma usa i file e gli strumenti locali.

## 6. Regole da tenere presenti

- **Branch e merge.** Mai lavorare su `main`. Una PR per task, in bozza, assegnata all'utente; il merge con squash lo fa l'utente, salvo una sua indicazione diversa. Dopo ogni merge, riallineare gli altri branch a `main` con un merge, senza force push. Le caselle del piano le aggiorna Claude, nella PR del task.
- **Proprietà dei file.**
  - `src/store/planning.ts` e `src/domain/metrics.ts` nascono dal Task 6.
  - `src/mywellness/client.ts`, i suoi test MSW e `docs/mywellness-api.md` appartengono alla corsia della #52.
  - Chi ha bisogno di una funzione di un'altra corsia non la scrive: la segnala nella propria PR.
- **Dati personali.** Nei testi si scrive «l'utente» e `<DASHBOARD_HOSTNAME>`. I log pubblici di Actions contengono solo conteggi, durate ed exit code. Non si scrive mai a mano su `sessions` e `timeseries`, e un `DELETE` su D1 richiede la conferma esplicita dell'utente.
- **Evidenza.** Prima di dire «fatto» si incolla l'output di `npm test`, `npm run lint` e `npm run typecheck` con l'exit code. La revisione indipendente la fa `.claude/agents/reviewer.md`, che riceve solo gli SHA, la spec, il task e `CLAUDE.md`.
